# File and storage API checklist

## Upload

- [ ] Large uploads go directly to object storage with a signed request. They do not pass through application servers.
- [ ] The signed request is short lived and bound to a server-chosen key, a maximum size and a content type. The caller cannot choose the path.
- [ ] A maximum size is enforced by the storage layer or the edge, before the bytes are accepted, not after. A presigned PUT on S3 does not bound the size by itself: use a presigned POST policy with a content length range, or verify the size on completion and delete.
- [ ] Creating the file resource accepts an idempotency key. Completing an upload twice is harmless.
- [ ] Files above a threshold use multipart or resumable upload, and a dropped connection resumes. The tus protocol and the IETF resumable uploads draft are the open options, and each cloud has its own.
- [ ] Each part, and the whole file, is verified by checksum.
- [ ] Unfinished uploads expire and their parts are deleted by a lifecycle rule.
- [ ] Upload rate and count are limited per caller, and counted against a quota.

## Validation

- [ ] The type is detected from the content, and compared with an allowlist. The file name's extension and the client's content type are not trusted.
- [ ] File names from clients are stored as metadata only. The storage key is generated by the server. Path traversal through a name is impossible.
- [ ] Files are quarantined until scanned for malware. A file that fails is never served.
- [ ] Archives are not unpacked without limits on total size, file count and depth.
- [ ] Images have limits on pixel dimensions as well as bytes, since a small file can decode to gigabytes.
- [ ] Metadata that may be private, such as location in photographs, is stripped where the product does not need it.
- [ ] Documents that can carry active content (HTML, SVG, PDF, office macros) are treated as hostile.

## Processing

- [ ] Conversion, thumbnailing and text extraction run asynchronously, with the file's state visible (uploaded, scanning, ready, rejected).
- [ ] Processors run in a sandbox with no network access and with limits on time, memory and output size.
- [ ] Media and document libraries are kept patched. They are a common source of remote code execution.
- [ ] Processing is idempotent, so a retried job does not create duplicate derived files.
- [ ] Derived files inherit the access rules of the original.

## Storage

- [ ] Buckets are private. Public access is blocked at the account level unless a bucket is public on purpose.
- [ ] Objects are encrypted at rest. Keys are per tenant where that has been promised.
- [ ] Tenants are separated by key prefix at least, and the application cannot build a key that crosses the prefix.
- [ ] Versioning or a soft delete window protects against accidental deletion and ransomware.
- [ ] Storage credentials used by the application have the least rights they need, and are not long-lived keys in code.
- [ ] Listing a bucket is not available to callers.

## Download

- [ ] Every download checks that the caller may read that file (OWASP API1), then issues a signed link with a lifetime of minutes.
- [ ] Signed links are treated as secrets: they are not logged, and they are not placed where a referrer header would leak them.
- [ ] User files are served from a separate domain with no cookies for the main application, with `Content-Disposition: attachment` for anything not known to be safe to show, and with `X-Content-Type-Options: nosniff`.
- [ ] The content type served is the one the server detected.
- [ ] Range requests work, so large downloads resume and media can seek.
- [ ] Downloads are cacheable where the content is immutable, using a key that includes a content hash.
- [ ] Revoking access takes effect within the lifetime of a link, and that lifetime is short enough for this to matter.
- [ ] Download volume is limited per caller, and bulk download is a separate, asynchronous feature.

## Import from a URL

- [ ] The address is resolved and checked against private, loopback, link-local and cloud metadata ranges, and the check is repeated after redirects (OWASP API7).
- [ ] Only HTTP and HTTPS are allowed. Size and time are limited.
- [ ] The fetch runs from an isolated network with no access to internal services.

## Sharing

- [ ] Share links are long random tokens, can expire, can be revoked, and can require sign-in.
- [ ] A share grants a named level of access to a named scope. Sharing a folder does not expose its parent.
- [ ] Access by link is logged.
- [ ] Public links are rate limited and can be reported.

## Quotas, lifecycle and deletion

- [ ] Quotas are enforced before upload starts, with a specific error.
- [ ] Retention periods are explicit per kind of file.
- [ ] Deletion is a pipeline: the original, every derived file, search indexes, caches and edge copies. It has a stated completion time.
- [ ] Legal holds can suspend deletion.
- [ ] Orphaned objects with no file record are found and removed by a regular job.

## Abuse

- [ ] Uploads of illegal content have a detection and reporting path where the law requires one, and a fast takedown.
- [ ] Your storage cannot be used as free hosting: quotas, type limits and hotlink controls.
- [ ] Malware distribution through share links is monitored.
