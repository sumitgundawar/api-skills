# gRPC and internal service API checklist

## Proto compatibility

- [ ] Field numbers are never reused or changed. Removed fields have their numbers and names marked `reserved`.
- [ ] Field types are not changed, apart from the few pairs the Protocol Buffers documentation lists as compatible.
- [ ] Fields are not moved into or out of a `oneof` without checking the documented rules.
- [ ] Enums have a zero value that means unspecified. Receivers handle unknown enum values.
- [ ] Packages carry a version (for example `orders.v1`). A breaking change is a new package, and both are served during migration.
- [ ] Package, service and method names are stable, because they form the request path.
- [ ] A breaking-change detector (for example `buf breaking`) and a linter run in CI against the published version.
- [ ] If the same messages are also served as JSON, field names are stable too, since JSON uses names where the binary form uses numbers.
- [ ] Presence matters where "not set" differs from the default: `optional` or wrapper types are used.
- [ ] Generated code is published as versioned packages, or generated by consumers from a registry. It is not copied by hand.

## Message design

- [ ] Each method has its own request and response message, so each can grow.
- [ ] Lists are paginated with a page token and a server-set maximum.
- [ ] Partial updates use a field mask.
- [ ] Money, time and durations use well-known or shared types, not floats and strings.
- [ ] Messages have a size limit that is known and enforced. The default limit on a received message is 4 MB in most gRPC implementations. Large payloads are streamed or sent by reference.
- [ ] Renaming a field is safe on the binary wire and still breaks generated code and the JSON form. Treat it as breaking.

## Deadlines and cancellation

- [ ] Every call sets a deadline. There is no default of "wait for ever".
- [ ] The remaining deadline is propagated to calls further down, and each hop leaves time for its own work.
- [ ] Servers check for cancellation and stop work when the caller has gone.
- [ ] Deadlines are chosen from measured latency, not copied.

## Retries and hedging

- [ ] Retries happen at one layer of the chain. Google's SRE book shows how retries at several layers multiply.
- [ ] A retry budget caps retries as a share of requests, per client. gRPC's own retry throttling in the service config is the built-in form of this.
- [ ] Only methods that are safe to repeat are retried: reads, or writes that carry a request identifier the server deduplicates on.
- [ ] Retries use exponential backoff with jitter, and honour server pushback.
- [ ] Only the status codes that mean "try again" are retried, typically UNAVAILABLE. DEADLINE_EXCEEDED on a write means the outcome is unknown.
- [ ] Hedged requests, if used, are for idempotent reads and are budgeted.
- [ ] Mesh or proxy retries and application retries are not both switched on for the same call.

## Errors

- [ ] Standard status codes are used with their documented meanings. INVALID_ARGUMENT, NOT_FOUND, ALREADY_EXISTS, FAILED_PRECONDITION, ABORTED, RESOURCE_EXHAUSTED and UNAVAILABLE are not interchangeable.
- [ ] Structured details use the standard error model messages (for example `ErrorInfo`, `RetryInfo`, `BadRequest`).
- [ ] Internal detail from deeper services is not passed up to external callers.
- [ ] A service that maps gRPC to HTTP uses the standard mapping of codes.

## Load and overload

- [ ] Each server limits concurrent calls and sheds with RESOURCE_EXHAUSTED, or with UNAVAILABLE plus retry pushback, before it runs out of memory or threads. A bare UNAVAILABLE invites the retries you are trying to shed.
- [ ] Requests carry a priority or criticality, set at the edge and propagated.
- [ ] Per-caller limits exist between internal services, so one caller's bug cannot starve the others.
- [ ] Load balancing is per call (client-side, or a proxy that understands HTTP/2). A connection-level balancer sends every call on a connection to one backend.
- [ ] Connections have a maximum age, so new backends receive traffic.
- [ ] Keep-alive settings agree between clients, servers and proxies.
- [ ] Health checking uses the standard health service, and reports not serving while starting and draining.
- [ ] Shutdown drains: stop accepting, finish in-flight calls, then exit.

## Streaming

- [ ] Streaming is used where it is needed, not as a default. Unary calls are easier to balance, retry and observe.
- [ ] Flow control is respected. A slow reader slows the writer, and buffers are bounded.
- [ ] Long-lived streams have a maximum lifetime and clients reconnect with backoff and jitter.
- [ ] A stream can resume from a position, or the client can tell what it missed.
- [ ] Authorisation is re-checked on long-lived streams.

## Identity and access

- [ ] Services authenticate each other with mutual TLS or signed tokens, with identities issued automatically and rotated (for example SPIFFE identities).
- [ ] Authorisation is per method and per caller. Being inside the network grants nothing.
- [ ] The end user's identity is carried explicitly, and services check it themselves. A service does not act with its own broad rights on a user's behalf without a check.
- [ ] Server reflection is off, or restricted, outside development.
- [ ] Sensitive fields are marked and are redacted from logs and traces.

## Observability

- [ ] Every call propagates trace context.
- [ ] Metrics exist per method and per caller: rate, errors by code, latency percentiles.
- [ ] Deadline-exceeded and cancelled calls are counted separately from errors.

## Edges

- [ ] Browser access uses gRPC-Web or Connect, or a JSON gateway, with the same authorisation.
- [ ] A REST mapping, where offered, is generated from annotations and is covered by the same compatibility checks.
- [ ] Public callers never reach internal services directly.
