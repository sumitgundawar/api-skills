# 5. Idempotency

The network will deliver some requests twice and lose some responses. A client cannot tell "it failed" from "it worked and I did not hear". Every state-changing operation must be safe to repeat.

## Checklist

- [ ] GET, HEAD, PUT and DELETE are idempotent by construction. Verify that they really are.
- [ ] Every POST and PATCH that changes state accepts an `Idempotency-Key` header. For anything that moves money or sends a message, require it.
- [ ] The key is generated by the client, has enough entropy (a UUID is fine), and contains no personal data.
- [ ] The key is scoped to the caller. The uniqueness constraint is on (account, key), not on the key alone.
- [ ] The server stores a fingerprint of the request with the key. The same key with a different body is rejected with a clear error.
- [ ] Two requests with the same key that arrive at the same time do not both execute. One wins. The other gets a conflict response it can retry.
- [ ] The in-flight marker carries a lease time. After it lapses, a retry takes the operation over from the last recovery point, so a worker that died does not leave the key answering 409 until it expires.
- [ ] Only finished outcomes are stored for replay. A 5xx means the outcome is unknown, so do not replay it unless you have decided to, as Stripe v1 does.
- [ ] Where the write is local, the key record and the business write are committed in the same database transaction.
- [ ] Where the write is a call to another system, no transaction can span it. Record the intent first, pass a derived key downstream, and record the outcome afterwards.
- [ ] Calls to other systems made inside the operation carry their own idempotency keys derived from yours.
- [ ] Keys expire. Publish the retention period. It must be longer than the longest retry horizon of any client. After expiry a retry creates a duplicate, so keep a natural unique constraint as the backstop.
- [ ] Webhook receivers deduplicate on the event identifier, because senders deliver at least once.

## Choose your replay behaviour

Two published models, both from Stripe:

- **Replay the first result** (Stripe API v1): keys are kept for at least 24 hours. A retry returns the status and body of the first attempt, even if it was a 500. Simple and predictable. A request that failed validation or collided with a concurrent one is not saved, so it can be retried.
- **Resume the work** (Stripe API v2): keys are kept for 30 days. If the first attempt succeeded, the retry returns the result without doing the work again. If it failed part way, the retry carries on. Better for multi-step operations. Harder to build.

For either, model the operation as phases separated by calls to outside systems, and record a recovery point after each phase. A retry reads the recovery point and continues from there.

## Tests to write

1. Send the same request twice with the same key. Expect one side effect and two identical responses.
2. Send two requests with the same key at once. Expect one side effect.
3. Send the same key with a different body. Expect a rejection.
4. Kill the process between the business write and the response. Retry. Expect one side effect.

## Standards status

The IETF draft for the `Idempotency-Key` header (draft-ietf-httpapi-idempotency-key-header-07) expired in April 2026 without becoming an RFC. The header is a de facto standard anyway. Use the name, and document your own semantics.
