# 5. Idempotency

The network will deliver some requests twice and lose some responses. A client cannot tell "it failed" from "it worked and I did not hear". Every state-changing operation must be safe to repeat.

## Checklist

- [ ] GET, HEAD, PUT and DELETE are idempotent by construction. Verify that they really are.
- [ ] Every repeat-sensitive operation accepts an `Idempotency-Key` header. That normally includes state-changing POST and PATCH operations. For anything that moves money or sends a message, require it.
- [ ] The key is generated by the client, has enough entropy (a UUID is fine), and contains no personal data.
- [ ] Scope the key to the authority and operation. The uniqueness constraint is on `(tenant or principal, operation, key)`, not on the key alone.
- [ ] The server stores a fingerprint of the request with the key. The same key with a different body is rejected with a clear error.
- [ ] Claim the key atomically, for example with `INSERT ... ON CONFLICT DO NOTHING`. Only the winner starts work. A duplicate loads the existing row: a matching request gets the stored result or a documented `PENDING` response; a different fingerprint is rejected.
- [ ] For long or externally mediated work, `PENDING` and `UNKNOWN` return the same stable operation resource on the original request and every duplicate, commonly `202 Accepted` with `Location` or the project's equivalent. Do not use a generic 5xx that encourages a caller to invent a fresh key.
- [ ] The in-flight marker carries a lease time and a recovery point. After a lease lapses, reconcile any external side effect by its provider or business reference before taking over. Never assume that a timeout or dead worker means the downstream operation failed.
- [ ] Model `PENDING`, `SUCCEEDED`, definitive failure and `UNKNOWN` explicitly. Replay final outcomes according to the published policy, and never turn an unknown outcome into a fresh attempt. Stripe v1 deliberately stores and replays the first response, including a 500.
- [ ] Where the write is local, the key record and the business write are committed in the same database transaction.
- [ ] Where the write is a call to another system, no transaction can span it. Durably record a `PENDING` intent and a provider-searchable business reference before the call, pass that reference and a stable derived key downstream, and record the provider's response identifier and outcome afterwards.
- [ ] Calls to other systems made inside the operation carry their own idempotency keys derived from yours.
- [ ] Keys expire. Publish the retention period. Keep your record beyond the longest client retry and internal reconciliation horizon; do not shorten it merely because a downstream provider forgets its key sooner. After that provider window, reconcile by the provider or business reference before retrying. Keep a natural unique constraint as the final backstop.
- [ ] Retry a downstream operation after an unknown outcome only when lookup conclusively proves that no operation occurred and the original request is still valid. If lookup is inconclusive, keep the resource `UNKNOWN` and escalate or reconcile manually. Never create a fresh attempt merely because the downstream idempotency window expired.
- [ ] Webhook senders deliver at least once. A receiver persists an inbox record, then applies the business effect and marks that record processed in one local transaction, so deduplication cannot hide a lost effect.

## Choose your replay behaviour

Two published models, both from Stripe:

- **Replay the first result** (Stripe API v1): keys are kept for at least 24 hours. A retry returns the status and body of the first attempt, even if it was a 500. Simple and predictable. A request that failed validation or collided with a concurrent one is not saved, so it can be retried.
- **Resume the work** (Stripe API v2): keys are kept for 30 days. If the first attempt succeeded, the retry returns the result without doing the work again. If it failed part way, the retry carries on. Better for multi-step operations. Harder to build.

For either, model the operation as phases separated by calls to outside systems, and record a recovery point after each phase. A retry reads the recovery point and continues from there.

## Tests to write

1. Send the same request twice with the same key. Expect one side effect and the documented replay result: the identical first response for replay-first semantics, or the current result for resume semantics.
2. Send two requests with the same key at once. Expect one side effect.
3. Send the same key with a different body. Expect a rejection.
4. Kill the process between the business write and the response. Retry. Expect one side effect.
5. Make a downstream provider complete the operation but lose the response. Retry and reconcile by the same provider or business reference. Expect no second side effect.
6. Make the provider lookup inconclusive. Expect the same stable `UNKNOWN` resource and no second downstream call.

## Standards status

The IETF draft for the `Idempotency-Key` header (draft-ietf-httpapi-idempotency-key-header-07) expired in April 2026 without becoming an RFC. The header is a de facto standard anyway. Use the name, and document your own semantics.
